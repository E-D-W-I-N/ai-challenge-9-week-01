# Контракт сценария

Один день челленджа = одна папка `day-NN/` = один файл `day-NN/scenario.py`,
который объявляет `SCENARIOS` — список сценариев дня (`app.schema.Scenario`).
Стенд подхватывает их сам — править `app/` ради нового дня не нужно и запрещено.

Сценариев в дне обычно несколько: каждый сценарий — это 1–3 колонки, которые
целиком влезают в кадр на записи экрана. Семь колонок в одном ряду дадут
горизонтальный скролл, и зритель не увидит сравнения, ради которого день
и снимают. Разбивайте день по пунктам задания: один пункт — один сценарий,
переключение в сайдбаре становится точкой монтажной склейки.

## Минимальный день

```python
from app.schema import Scenario, Session

SCENARIOS = [
    Scenario(
        id="day-02-format",
        title="Формат ответа",
        description="Что демонстрируем. Пользователь читает это до нажатия «Старт».",
        watch_for="На что смотреть на записи экрана. Судье не уходит.",
        layout="split",               # single | split
        sessions=[
            Session(
                label="Без формата",
                model="meta-llama/llama-3.1-8b-instruct",
                messages=[{"role": "user", "content": "..."}],
                note="Подпись под колонкой.",
            ),
            Session(
                label="JSON",
                model="meta-llama/llama-3.1-8b-instruct",
                messages=[{"role": "user", "content": "... верни JSON ..."}],
                response_format={"type": "json_object"},
                note="Тот же вопрос, жёсткий формат.",
            ),
        ],
    ),
    Scenario(id="day-02-length", title="Длина ответа", ...),
]
```

**Порядок внутри `SCENARIOS` значим**: он задаёт порядок сценариев дня в сайдбаре
и должен совпадать с порядком пунктов задания дня.

Стенд понимает и другие формы — переписывать уже готовые дни под новый контракт
не нужно:

| Форма | Когда |
|---|---|
| `SCENARIOS: list[Scenario]` | Основной контракт |
| `def get_scenarios() -> list[Scenario]` | То же, если список нужно собрать кодом |
| `SCENARIO: Scenario` | День ровно с одним сценарием |
| `def get_scenario() -> Scenario` | То же фабрикой |

Что-то одно из четырёх. Если объявлено несколько, выигрывает `SCENARIOS`.

## Правило `id`

`id` **уникален глобально** и **начинается с имени папки**:
`day-02-format`, `day-02-length`, `day-02-stop`. День с одним сценарием может
назвать его просто `day-02`.

Нарушение правила, дубликат `id`, падение `scenario.py` при импорте — на
каждый такой случай реестр кладёт ошибку в `registry.errors()`, и её текст
виден в сайдбаре под списком. Ломается только виноватый день (целиком, всеми
своими сценариями), остальные дни грузятся как обычно.

`day-01` — невалидное имя пакета Python (дефис), поэтому реестр грузит файл через
`importlib.util.spec_from_file_location`. Из-за этого **относительные импорты
внутри `day-NN/` не работают**: пишите весь день в одном `scenario.py`
и импортируйте только из `app.schema`.

## Как это выглядит в UI

Сайдбар группирует сценарии по дням: заголовок `День 02`, под ним сценарии дня
в порядке из `SCENARIOS`. Дни идут по возрастанию номера — `day-9` раньше `day-10`.
Заголовок стенд берёт из имени папки, отдельного поля для него нет.

`/api/scenarios` отдаёт плоский список (в том же порядке, у каждого сценария есть
`day` и `day_title`) и разбивку `days: [{id, title, scenario_ids}]`.

## Серия прогонов: `repeats`

Некоторые эффекты статистические: на одном ответе их не видно. День 4 сравнивает
температуры, и при одном вызове на колонку `t=0` и `t=1.2` выглядят похоже —
разброс проявляется только на нескольких прогонах одного и того же запроса.

```python
Session(label="t = 1.2", model="openai/gpt-4o-mini", messages=_MSG,
        temperature=1.2, repeats=3)
```

Колонка делает `repeats` **последовательных** вызовов: важна предсказуемость
и цена, а не скорость. Каждый прогон стенд рисует в ленте отдельным сообщением
с подписью «прогон N из M» и своей строкой метрик. Под колонкой стенд считает
**долю уникальных ответов**, сравнивая тексты дословно после `strip()`.

Цена растёт кратно: `repeats=3` — это втрое дольше и втрое дороже. Ставьте
повторы только там, где без них вывод дня недоказуем.

**По умолчанию `repeats=1`**, и тогда всё ровно как раньше: один вызов, никаких
«прогон 1 из 1» в ленте, нет блока уникальности и в потоке нет ни одного
repeat-события. Сценарии, которые повторов не просили, ничего не замечают.

| Что | При `repeats = 1` | При `repeats > 1` |
|---|---|---|
| события потока | `session_start` → `delta` → `session_done` | плюс `repeat_start` / `repeat_done` / `repeat_error` и поле `repeat` в `delta` и `metrics` |
| панель метрик | метрики единственного вызова | метрики текущего прогона, подписанные «метрики прогона N из M»; метрики каждого прогона остаются в ленте под его ответом |
| `session_done` | `text`, `metrics` | плюс `repeats`, `texts` (все ответы) и `unique` |
| судье уходит | один ответ | все ответы серии и доля уникальных |

Упавший прогон серию не останавливает: стенд помечает его `repeat_error`,
остальные прогоны идут дальше, а в уникальность и в суммы попадают только
удавшиеся. Колонка считается провалившейся, только если не удался ни один
прогон. Обрыв клиента гасит и незапущенные повторы: незачем платить за серию,
которую никто не увидит.

## Вердикт: `judge_questions` и `judge_model`

Задание дня почти никогда не заканчивается словом «покажите»: едва ли не каждый
день просит **сравнить** и **сформулировать вывод**. Колонки рядом этот вывод
не дают — его выносит модель-судья.

```python
Scenario(
    id="day-04-temperature",
    ...
    judge_questions=[
        "Отличаются ли ответы между собой и в чём именно?",
        "Для каких задач лучше подходит каждая температура?",
    ],
    # judge_model="anthropic/claude-3.5-sonnet",   # необязательно
)
```

Как только все колонки сценария отработали, стенд делает **один** дополнительный
вызов к отдельной модели и стримит её ответ в блок «Вердикт» между колонками
и сводкой.

### Что видит судья, а что нет

| Уходит судье | Не уходит |
|---|---|
| `judge_questions` — вопросы дня | `watch_for` |
| `description` сценария | |
| по каждой колонке: `label`, `note`, отличающие параметры (модель, `temperature`, `max_tokens`, `stop`, `response_format`), краткие метрики (время, токены, стоимость, `finish_reason`) и полный текст ответа | |
| у колонки с `repeats > 1` — **все** ответы серии, пронумерованные по прогонам, и доля уникальных | |

**`watch_for` судье не отправляется** — и это не мелочь реализации, а правило.
Это режиссёрская подсказка ведущему: в ней по замыслу написано, какая колонка
что покажет и где ошибётся. Судья, получивший подсказку, сверялся бы с ней
вместо того, чтобы читать ответы. А автору дня пришлось бы вычищать из поля,
написанного для человека, всё, что подсказывает вердикт. Пишите `watch_for` для
ведущего и ни в чём себе не отказывайте: эталонный ответ, предсказание «левая
колонка сядет в ловушку», что именно ловить на записи.

`description` судье уходит — без него он не поймёт, что за эксперимент перед
ним. Поэтому **эталонов и предсказаний в `description` быть не должно**:
это описание демонстрации, а не её разбор. Разбор — в `day-NN/README.md`,
он не уходит никуда.

У колонки с `repeats > 1` судья получает все ответы серии, а не последний:
без этого на вопрос про разнообразие он не ответит.

**Пустой `judge_questions` — блока нет и вызова нет.** Это по умолчанию: день,
который ничего не сравнивает (например, День 1), за судью не платит.

### Как формулировать вопросы

Своими словами, прямо из текста задания дня, по одному вопросу на пункт.
Не «оцени качество», а то, что действительно спрашивают: «Отличаются ли ответы
и в чём», «Какой способ дал наиболее точный результат», «Для каких задач лучше
подходит каждая настройка». Судья отвечает по каждому вопросу и заканчивает
абзацем-вердиктом, так что три-четыре вопроса — потолок, иначе ответ не влезет
в кадр.

### Модель судьи

По умолчанию `app.main.JUDGE_MODEL` — модель заметно крупнее подопытных.
Весь смысл в том, что судит **другая** модель, а не одна из колонок;
`judge_model` в сценарии переопределяет дефолт. Совпадение с моделью колонки
не запрещено, но стенд пишет об этом прямо в блоке — зритель должен видеть,
что судья судит сам себя.

Судья зовётся с `temperature=0.2`: нужна повторяемость вердикта, а не творчество.

### Что бывает при сбоях

| Ситуация | Поведение |
|---|---|
| колонка упала | судья вызывается, но про эту колонку ему сказано «НЕ ОТРАБОТАЛА» и вердикт по ней выносить запрещено |
| упали все колонки | вызова нет, блок объясняет, что судить нечего |
| судья упал | ошибка показана в блоке, колонки и сводка не страдают |
| прогон прерван (закрыли вкладку, переключили сценарий) | судья не вызывается: платить за вердикт по неполным данным незачем |

Стоимость судьи попадает в сводку **отдельной строкой** и не смешивается
с суммой по колонкам.

События потока: `judge_start` (модель, вопросы, совпадения с колонками),
`judge_delta`, `judge_metrics`, `judge_done`, `judge_error`, `judge_skipped`.

## Поля Session

| Поле | Смысл |
|---|---|
| `label` | Заголовок колонки. Уникален внутри сценария — на него ссылается `depends_on` |
| `model` | id модели OpenRouter |
| `messages` | Сообщения в формате OpenAI chat |
| `temperature`, `max_tokens`, `stop`, `response_format` | Уходят в запрос как есть, если не `None` |
| `repeats` | Сколько раз подряд прогнать колонку одним и тем же запросом. По умолчанию 1 |
| `depends_on` | `label` другой сессии. Колонка ждёт её и подставляет её вывод вместо `{{depends_on}}` |
| `note` | Подпись под колонкой: чем эта колонка отличается от соседней |
| `extra_body` | Дополнительные поля запроса (`seed`, `provider.order`, `provider.allow_fallbacks`) |

Сессии без `depends_on` стартуют одновременно. Каждая колонка — один запрос
сценария: при `repeats = 1` это ровно один вызов модели, при `repeats > 1` —
серия одинаковых вызовов подряд.

Если донор не отдал ответ — упал с ошибкой или вернул пустой текст, — зависимая
колонка **не запускается**: подставлять нечего, а вызов с пустой подстановкой
стоил бы денег и дал бы бессмысленный ответ, который на записи выглядит как
работающий. Вместо вызова колонка получает `session_error` с текстом
«колонка пропущена: донор «…» не отдал ответ».

## Как выглядит колонка

Колонка — это чат: лента сообщений сверху, панель метрик под ней, поле ввода
в самом низу. Раскладка на всю высоту экрана: скроллится только лента внутри
колонки — метрики и поле ввода всегда остаются на месте. Горизонтального скролла
у страницы нет ни при какой ширине. Высоту колонки не отбирают ни «Вердикт»,
ни сводка: они встают **под** экраном колонок, и страница получает вертикальный
скролл, когда им перестаёт хватать места. Колонки делят ширину поровну;
на узком экране они встают друг под друга, по одной на экран.

Шапка сценария — одна строка: название, селектор модели на каждую колонку
и «Старт». `description` и `watch_for` спрятаны за кнопкой «О сценарии»
и по умолчанию свёрнуты — пользователь читает их перед записью и закрывает.
Писать их всё равно нужно: это часть контракта и единственное объяснение,
что за демонстрацию он смотрит.

Сообщения из `Session.messages` стенд показывает **сразу при выборе сценария**,
до нажатия «Старт»: зритель читает промпт, включает запись и только потом
запускает. `system` идёт приглушённым блоком и сворачивается по клику,
`user` — заметным пузырём, ответ модели дописывается снизу как `assistant`.

Поэтому промпт — часть кадра: пишите `messages` так, чтобы их можно было
прочитать на видео, а разницу между колонками (она обычно и сидит в промпте)
было видно с одного взгляда.

У колонки с `depends_on` до старта виден исходный текст: литерал
`{{depends_on}}` подсвечен, рядом пометка, чей вывод его заменит. На событии
`session_start` стенд перерисовывает ленту итоговым промптом — зритель видит,
что реально ушло в модель.

У колонки с `depends_on` в `session_start` приезжает ещё и поле `donor`:

```jsonc
"donor": {
  "label": "Модель пишет промпт",  // чей вывод подставлен
  "finish_reason": "length",        // чем закончился донор
  "truncated": true                 // finish_reason == "length": промпт подставлен урезанным
}
```

`truncated: true` означает, что донор упёрся в свой `max_tokens` и подставленный
промпт неполон — это стоит пометить в подписи под лентой, иначе на записи
не понять, почему ответ хуже ожидаемого.

## Ручной ввод и `POST /api/chat`

Под лентой каждой колонки есть поле ввода: пользователь дописывает свои вопросы
руками, до «Старта» и после. Enter отправляет, Shift+Enter переносит строку.
Ответ стримится в ленту как `assistant`, панель метрик колонки обновляется
по этому запросу. Без ключа поле недоступно и подписано, чего не хватает.

Диалог продолжается: в модель уходит **вся накопленная лента колонки** —
исходный `system`, исходный `user`, ответы сценария и все ручные сообщения.
Параметры берутся из `Session` этой колонки, модель — из её селектора.

Эндпоинт для этого — `POST /api/chat`. Тело:

```jsonc
{
  "model": "mistralai/mistral-small-3.2-24b-instruct",  // обязателен
  "messages": [                                          // обязательны, непустой список
    {"role": "system", "content": "..."},               // role: system | user | assistant
    {"role": "user", "content": "..."}                  // content: непустая строка
  ],
  "temperature": 0.7,          // всё ниже — необязательно, null = не слать
  "max_tokens": 300,
  "stop": ["\n\n"],
  "response_format": {"type": "json_object"},
  "extra_body": {"provider": {"allow_fallbacks": false}},
  "label": "Ответ"             // только для читаемости логов
}
```

Ответ — `text/event-stream` с теми же событиями, что и прогон сценария:

| Событие | Поля | Когда |
|---|---|---|
| `delta` | `text`, `metrics` | на каждый кусок ответа |
| `metrics` | `metrics` | пришёл `usage` — стоимость и токены |
| `error` | `message`, `metrics` | вызов не удался, поток закрывается |
| `done` | `text`, `metrics` | ответ закончен, `text` — весь ответ целиком |

Ошибки входа — `400` с текстом, который можно показать пользователю; без ключа —
`503` и объяснение про `.env`. Пятисотки эндпоинт не отдаёт: сбой самого вызова
приходит событием `error` внутри уже открытого потока.

## Прогон сценария и `overrides`

`GET /api/run/{id}` принимает необязательный query-параметр `overrides` — JSON,
которым UI подменяет параметры колонок перед прогоном:

```jsonc
{"Ответ": {"model": "openai/gpt-4o-mini", "temperature": 0.3, "max_tokens": 128}}
```

Ключи — существующие `label` колонок этого сценария, поля — только `model`,
`temperature` и `max_tokens`. Всё остальное принадлежит автору дня и подменить
это нельзя: `messages` — это сам сценарий, а подменённый `label` разъехался бы
с колонками в UI. Переданные поля заменяют значения сессии, непереданные
остаются как в сценарии, явный `null` снимает значение.

Проверяет `overrides` тот же код, что и тело `/api/chat`: на кривой `overrides`
эндпоинт отдаёт `400` с текстом (что именно не так и в какой колонке), а не `500`.

## Что стенд делает сам

- `provider: {"require_parameters": true}` на **каждом** вызове. Без него OpenRouter
  вправе увести запрос к провайдеру, который молча проигнорирует `temperature` или
  `stop`, и день покажет неправду. Дописывать это в `extra_body` не нужно.
- `usage: {"include": true}` — стоимость и reasoning-токены приходят в финальном чанке.
- Стриминг, TTFT, живой счётчик ток/с, заполнение контекста, сводка по прогону.
- Обрывает вызовы, когда клиент ушёл: закрытая вкладка, перезагрузка страницы или
  оборванный SSE гасят все сессии прогона, а не дают им дожечь токены в пустоту.
- Дропдаун моделей на каждую колонку с фильтрами по `supported_parameters`.
- Не запускает зависимую колонку, когда донору нечего было передать: пустая
  подстановка в модель не уходит.
- Зовёт модель-судью после прогона, если у сценария есть `judge_questions`, —
  один вызов, вердикт стримится в блок под колонками.

## Что должен сделать автор дня

1. Разбить задание дня на сценарии — по одному на пункт, 1–3 колонки в каждом.
2. Написать `day-NN/scenario.py` со `SCENARIOS` и осмысленными промптами.
3. Написать `day-NN/README.md`: что демонстрируем и что ловить на видео.
4. Проверить статически, что файл парсится и все сценарии видны реестру,
   а `errors()` пуст:

```bash
.venv/bin/python -c "from app import registry; print([s.id for s in registry.discover()], registry.errors())"
```

**Ничего не запускать.** Ни `uvicorn`, ни живых вызовов к LLM API. Прогон делает
пользователь сам, на запись экрана. Ключ авторам сценариев не нужен.

## Подводные камни провайдеров

Каждый пункт проверен и каждый ломает свой день молча.

- **`response_format={"type": "json_object"}`** возвращает 400 на моделях семейства
  OpenAI, если в самом промпте не встречается слово «JSON». Пишите его в промпт явно.
- **`stop` не даёт прямого сигнала**: стоп-строка в вывод не попадает, а
  `finish_reason` в обоих случаях `stop`. Наблюдаемый эффект даёт `max_tokens` →
  `finish_reason: length`.
- **Anthropic обрезает температуру на 1.0**: `temperature=1.2` вернёт 400. При этом
  `anthropic/*` честно перечисляет `temperature` в `supported_parameters`, так что
  фильтр по параметрам их пропустит. Для «горячих» температур модели этого семейства
  исключены из дропдауна отдельным флагом.
- **`T=0` на OpenRouter не детерминирован** (MoE, батчинг, роутинг). Писать «T=0
  даёт детерминизм» нельзя, если не закреплены `provider.order` и `seed`.
- **`:free`** всегда стоит 0 (сравнивать нечего), **`:batch`** — другая семантика
  задержки. Оба варианта отфильтрованы из каталога.
- **`allow_fallbacks: false`** нужен там, где меряют задержку и цену: иначе непонятно,
  чью задержку измерили. Кладите в `extra_body={"provider": {"allow_fallbacks": False}}`.
- **`usage.cost_details.upstream_inference_cost`** равен 0 без BYOK — в таблицы не класть.
- **Задержку меряйте медианой** минимум по трём прогонам с отброшенным прогревочным:
  первый вызов платит за DNS и TLS.

## Правило владения

Автор дня меняет **только** свою папку `day-NN/`. `app/`, `docs/`, `README.md`,
`requirements.txt`, `.gitignore` заморожены. Коммит — `git add day-NN`,
никогда `git add -A` или `git add .`: репозиторий публичный, а в `.env` лежит ключ.
Кажется, что нужна правка вне своей папки — шлите `escalation` оркестратору.
